# PlaceGame VIP 收菜客户端 —— 重新设计方案

> 版本：v2.3 设计稿（待评审，评审通过后进入实施）
> 范围：**界面与操作流程重构 + 设置与配置页 + 玩法自动化扩展**（街机/大乐透/内部市场/每日 Boss/智能换图/自动换装/副职业循环/自定义一键分解/装备捐赠/大号养成自动化），调度引擎按 **120 个小号**规模做并发化配套改造
> 现状参考：`docs/收菜逻辑与接口文档.md`；玩法接口来源：`../placegame-docs/游戏玩法与流程接口.md`
> v2.1 变更：原"v2 候选"玩法全部转入正式范围（§5），每个小号均参与；新增收菜后自动换装、到级自动换图、每日三类 Boss 流水线。
> v2.2 变更：新增副职业定时循环（§5.6）、按小号阶段的一键分解模板（§5.4）、小号装备一键捐赠公会（§5.5）、大号洗装备自动化（§5.11）。
> v2.3 变更：市场升级为**小号↔大号内部闭环**（求购/交付/改价/取消，§5.10）；强化/词条继承/强化继承纳入大号养成自动化（§5.11）；一键分解规则改为**界面完全自定义**（§5.4）；Boss 战前部署策略落地（§5.7，含词缀调研结论）。
> v2.4 变更：强化保护符起始等级 +7 → **+11**（§5.11）；UI 在五页面重构（M2）基础上进一步整体视觉优化（见 §4.0）。

## 1. 现状诊断：流程为什么不完善

### 1.1 界面层问题

| # | 问题 | 影响 |
|---|---|---|
| 1 | 所有功能挤在单页四个卡片里，无导航 | 120 个小号塞进一张表格，滚动地狱，无法聚焦 |
| 2 | 上手无引导：大号→建会→建小号→开始，顺序全靠 README | 新用户第一步就卡住（没建会时小号全部空转，只提示"大号尚未建会"） |
| 3 | 所有反馈走 `alert()` 弹窗 | 打断操作、无法批量、批量建小号结果一闪而过 |
| 4 | 账号表只有"阶段"一列 | 看不到等级、经验进度、下次收菜时间、今日任务完成情况、最近错误 |
| 5 | 无流水线总览 | 120 个小号处在 建角色/练级/待入会/已入会 各多少？全靠心算 |
| 6 | 日志只有最近 30 条原始表 | 无法按账号/任务/状态过滤，失败被刷掉后无从排查 |
| 7 | 运行状态只有一个 badge | 不知道调度器此刻在跑哪个账号、卡在哪一步 |

### 1.2 配置层问题

`SchedulerOpts` 全部写死在 `lib.rs::default_opts()`：

- `tick_secs = 30`、`idle_hours_capacity = 12.0`（90% 触发）、`join_target_level = 12`
- `deny_donate` 保留列表 4 项硬编码
- `guild_enabled = true` 无开关界面

改任何一项都要改代码重新编译，违背"VIP 客户自用工具"的定位。

### 1.3 调度层问题（120 号规模的硬约束）

| # | 问题 | 量级估算 |
|---|---|---|
| 1 | `one_pass` 对所有账号**串行**处理 | 单账号一轮收菜约 8-10 个请求 × 300ms ≈ 3s；120 个小号全量一轮 ≈ **6-10 分钟**，练级期更长 |
| 2 | 失败即记录、下轮同等重试 | 无退避，会话失效/服务端 503 时 120 个号每 30s 轮流撞墙 |
| 3 | 无全局请求节流 | 并发化之后必须配节流，否则单设备 120 号高频请求等于自我 DoS + 风控风险 |
| 4 | 跨天漏跑不补 | 客户端关了一天，`daily:昨天` 永远不会补（收益本身不丢，但签到/活跃宝箱会断） |

> 设计原则：**收菜逻辑（文档 §1.3 的顺序与幂等）保持不变**——它已经是对的。本方案只重构呈现、配置、调度外壳。

## 2. 新信息架构

从"单页四卡片"改为**左侧导航 + 五个页面**：

```
┌─────────────────────────────────────────────────────┐
│ 🪙 PlaceGame VIP          ● 运行中  ▶/⏸  ⚡同步一轮 │
├──────────┬──────────────────────────────────────────┤
│ 📊 总览   │                                          │
│ 👥 账号   │            （当前页面内容）                │
│ 🏰 公会   │                                          │
│ 📜 日志   │                                          │
│ ⚙️ 设置   │                                          │
└──────────┴──────────────────────────────────────────┘
```

- 顶部栏常驻：运行状态、开始/停止、立即同步（全局操作，任何页面可达）
- 左侧导航常驻：当前页面高亮
- 首次启动（无任何账号）时**强制进入引导流程**（见 §3）

## 3. 引导式上手流程（Onboarding Wizard）

解决"不知道先干什么"的核心问题。检测条件：`accounts` 为空或 `main_guild_id` 为空 → 总览页顶部显示引导卡片，可一键进入向导。

```
第 1 步：添加大号                第 2 步：创建公会            第 3 步：批量创建小号
┌──────────────────────┐   ┌──────────────────────┐   ┌──────────────────────┐
│ ○ 登录已有账号        │   │ 公会名: [VIP 军团  ]  │   │ 数量: [120]          │
│   账号/密码           │ → │ 宣言:  [          ]  │ → │ 职业: [战士 ▼]       │
│ ○ 创建游客大号        │   │ 自动设为免审核入会 ☑  │   │ [开始创建]           │
│ [下一步]             │   │ [创建公会]           │   │ 进度条 45/120        │
└──────────────────────┘   └──────────────────────┘   └──────────────────────┘
                                                          ↓ 完成
                                                    自动开启调度 → 总览页
```

- 每步可跳过（跳过即留待后续手动操作）
- 批量创建小号从"alert 报结果"改为**页面内进度条 + 实时成功/失败计数**，失败的可一键重试
- 完成后自动 `start_daemon`，进入总览页

## 4. 各页面详细设计

### 4.0 整体视觉优化（v2.4 新增）

五页面信息架构不变，但对整体视觉做系统性升级——纯静态三件套不引入框架，用 CSS 设计令牌统一风格：

| 方面 | 约定 |
|---|---|
| 设计令牌 | `:root` 集中定义色板/圆角/间距/字号阶梯（`--c-*` / `--r-*` / `--sp-*` / `--fs-*`），全部页面引用，禁裸值 |
| 主题 | 跟随系统明暗（`prefers-color-scheme`），暗色一套令牌覆盖 |
| 布局 | 左侧导航收窄为图标+文字（64px 收起态可切换）；内容区 max-width 居中；卡片化区块 + 8px 网格间距 |
| 数据可视化 | 漏斗改横向分段条（hover 显示数量）；任务完成度改环形进度；账号表格支持粘性表头 + 行状态色（错误行淡红底） |
| 状态反馈 | 全部操作 Toast 化；按钮 loading 态；空状态插画位（无账号/无日志时给引导而不是空白） |
| 信息密度 | 账号页默认紧凑行高，可切"舒适/紧凑"；120 行表格虚拟滚动或分页（50/页） |
| 字体 | 系统字体栈；数字统一 `font-variant-numeric: tabular-nums`（表格数字对齐） |

> 目标：工具型应用，信息效率优先、克制的点缀；不以装饰牺牲可读性。

### 4.2 👥 账号页

- **Tab 切换**：大号 | 小号（默认小号，大号通常只有 1 个）
- **小号表格增强列**：

| ID | 昵称 | 职业 | 等级 | 阶段 | 今日收菜 | 今日捐献 | 最近错误 | 启用 | 操作 |
|---|---|---|---|---|---|---|---|---|---|

- **过滤与搜索**：按阶段多选过滤、按昵称/ID 搜索、只看"有错误"开关
- **批量操作**：勾选 → 批量启用/停用、批量删除、批量立即收菜

- 公会信息卡：名称、guildId、成员数/上限、免审核开关状态

- 未建会时此页显示"前往创建"引导按钮

### 4.4 📜 日志页

- 过滤器：账号（下拉/搜索）、任务类型（collect/level/join/donate/guild_*）、状态（成功/失败）、时间范围（今天/昨天/7 天）
- 默认只显示**最近 200 条 + 失败置顶**选项
- 失败行支持"立即重试该账号该任务"按钮
- 保留轮询刷新（3s），但加"暂停自动刷新"开关（排查时不被滚动打断）

## 5. 玩法自动化扩展（v2.1 新增，每个小号均参与）

> 接口来源：`../placegame-docs/游戏玩法与流程接口.md` §3.5/3.9/3.13/3.14/3.10 与 §5.2 清单。
> 总原则：**全部按北京日幂等**（run_key 机制复用），单步失败只影响该账号该玩法，下轮退避重试。

### 5.1 扩展后的单账号每日流水线（顺序有讲究）

```
小号：
1. 收菜轮（现有逻辑不变：保活→bootstrap→邮件→签到→活跃→成就→挂机收益）
2. 副职业循环 professions_loop   # settle 收进度 → 队列补满 → 补给（口粮/首领药剂）就位
3. 自动换装 auto_equip_best      # 背包 vs 穿戴逐部位比评分，先变强
4. 装备捐赠 guild_equip_donate   # 好装备先捐公会养大号（换装之后，好货不会被自己穿着）
5. 一键分解 auto_decompose       # 按当前阶段的分解模板清低价值装备（换装+捐赠之后，绝不误伤）
6. 智能换图 ensure_best_map      # 等级/战力达标即换挂机效率最高的可进图
7. 每日 Boss boss_daily          # 装备换好、药剂就位、图换好再打，胜率最高
8. 街机免费轮 arcade_free        # 纯收益，失败无损失，放最后
9. 大乐透 lottery（可选）         # 购票花金币，默认关
10. 内部市场 market_internal（可选）# 交付大号求购/溢出挂单/超时撤单，见 §5.10

大号：收菜轮 → 副职业循环 → 养成自动化（继承→洗练→强化→强化继承，§5.11）→ 公会审批/分红 → 内部市场（求购/收货/维护）→ 街机/大乐透（同小号）
```

顺序原则：产出类（收菜/副职业）在前，变强类（换装/捐赠/分解/换图）居中，消费战力类（Boss）随后，纯附加（街机/大乐透/市场）收尾。中间任何一步失败不阻塞后续。**分解必须严格排在换装和捐赠之后**——这是防误销的硬约束。

### 5.2 自动换装（auto_equip_best）

- 数据：bootstrap state 的 `equipment`/`inventory` section，逐部位（weapon/armor/helmet/necklace/bracelet/ring/belt/boots/talisman/medal）比较"背包中可用装备"与"已穿戴装备"的**穿戴评分**。
- 动作：评分更高 → `POST /api/equipment/wear {equipmentId}`；换下的旧装备不自动处理（捐献/分解走现有公会捐献与手动流程，避免误销）。
- 排除：**锁定的装备不动**（`toggle-lock` 状态）；等级不够穿不上的跳过；绑定装备优先于未绑定（未绑定装备是公会捐献/市场货源，不往身上焊）。
- run_key：`equip:{today}:{n}`（每天可能多次收菜，换装跟随收菜轮，天然幂等——重复 wear 同一件无效果）。

### 5.3 智能换图（ensure_best_map）

- 触发：每次练级 tick + 每次收菜轮。
- 逻辑：从 `maps` section 取全部地图，过滤 `进入等级 ≤ player.level` 且 `进入战力 ≤ 当前战力`，按**挂机效率**取最高者；与当前图不同 → `POST /api/battle/change-map {mapKey}`。
- 现有 `level_once` 的"换最优图"逻辑收敛到这一个函数，练级期与收菜期共用，实现"到可进入下一等级时自动进入下一个地图"。

### 5.4 一键分解（规则界面完全自定义，auto_decompose）

低价值装备不囤、不捐，直接分解换金币/材料。接口用游戏自带的规则化一键分解：`POST /api/equipment/auto-decompose-rules {patch}` 保存规则 + `POST /api/equipment/auto-decompose {}` 执行。

**规则不是写死的模板，而是设置页里可编辑的规则表**——直接映射 `auto-decompose-rules` 的 patch schema（字段以联调 §5.13-7 确认为准）：

| 规则维度 | 设置页控件 | 说明 |
|---|---|---|
| 品质上限 | 多选（白/绿/蓝/紫/橙/红/金） | 勾选的品质进入分解范围 |
| 装备等级上限 | 数值输入 | 低于该等级才分解（防止误分解高等级过渡装） |
| 部位范围 | 部位多选 | 默认全部位 |
| 例外清单 | itemKey 列表 | 永不分解的指定装备 |

**按阶段各存一套**：`init` / `ready` / `joined` 三个阶段各有一组上述规则，界面分别编辑。内置三档预设作为起点（用户可在此基础上改）：

| 阶段 | 预设 | 默认规则 | 理由 |
|---|---|---|---|
| `init` 练级期 | 保守 | 品质 ≤ 白 | 练级期换装频繁，绿蓝都可能是提升，留 |
| `ready` 待入会 | 标准 | 品质 ≤ 绿 | 12 级后绿装基本无提升 |
| `joined` 已入会 | 激进 | 品质 ≤ 蓝 | 稳定期只要紫以上，蓝装直接变材料 |

- **切换时机**：`alt_phase` 变更时自动把该阶段的规则写入 `auto-decompose-rules`，随后每轮收菜后执行一次 `auto-decompose`。
- **安全网（优先级高于任何自定义规则，界面不可关闭）**：已穿戴、已锁定、未绑定装备一律不分解——未绑定装备是捐赠/内部市场货源（§5.5/§5.10），归捐赠流程处理，不归分解。
- run_key：`decompose:{today}:{n}`，跟随收菜轮；`auto-decompose` 本身服务端幂等（无可分解物返回空）。

### 5.5 装备一键捐赠公会（guild_equip_donate，养大号的关键链路）

现有小号只捐**材料**（`guild/donate`），但大号养装备靠的是**公会共享仓库**：小号捐装备入仓库 → 大号用 `equipment/redeem` 兑换出来穿/洗。

- 接口：`POST /api/guild/equipment/donate {equipmentId}`（逐件，"一键"由客户端遍历实现）。
- 捐献范围：**未绑定 + 未锁定 + 未穿戴**的装备中，品质 ≥ 阈值的（默认精良/蓝及以上——白绿走 §5.4 分解，蓝紫以上才值得大号 redeem）。
- 阈值可配（`opt.guild_equip_min_quality`），并与会长侧的"最低入库品质"（`equipment-donation-quality`）对齐，避免捐了入不了库。
- 大号侧：redeem 是贵重决策（消耗贡献），**客户端只做提醒不做自动兑换**——公会页显示"共享仓库可兑换 N 件（紫 x / 橙 y）"，由人点选。
- 执行位置：joined 阶段小号的每日流程，紧随换装之后、分解之前（见 §5.1 顺序约束）。
- run_key：`equip_donate:{today}`；仓库满时服务端报错，记录后跳过等扩容，不重试轰炸。

### 5.6 副职业定时循环（professions_loop）

四种副职业（采药/钓鱼/烹饪/炼金）共用一条执行队列，离线也跑——这是"睡着也在产出"的纯收益，120 个小号必须全挂上。

**循环逻辑（跟随调度 tick，无需单独定时器）**：

```
每轮处理账号时：
1. POST /api/professions/settle        # 收取已完成进度（队列为空也安全调用）
2. 若队列剩余 < 阈值 → /api/professions/queue/enqueue {actionKey, count}  # 补满
3. 补给就位检查：
   - 挂机口粮：supply/equip {supplyType:"food", itemKey}（有货才装，高阶盛宴优先）
   - 首领药剂：supply/equip {supplyType:"bossPotion", itemKey}（Boss 自动化 §5.7 的弹药）
```

- 副职业选择：每个小号固定一种（`opt.profession_key`，默认 `herbalism` 采药——原料是炼金/烹饪前置，泛用最广）；`professions/select` 只在未选定时执行一次。
- 动作选择：默认只挂**稳定采集**类动作（无原料依赖，永不断料）；加工类需要原料链，小号默认不碰（可配 `opt.profession_craft` 开启）。
- 永久专精：不可更改的贵重决策，**不做自动**，留手动。
- run_key：`prof_settle:{today}:{n}`（跟随收菜轮多次）；`prof_enqueue:{today}`（每日补满一次即可，队列耗尽时额外补）。

### 5.7 每日 Boss（boss_daily）

三类首领，消耗**首领门票**（保留列表已含 `boss_ticket`，见 §4.5 注意项）：

| 类型 | 策略 | run_key |
|---|---|---|
| 个人首领 personal | 每日 1 次：先 `boss/preview` 推演，**可胜才 challenge**；推演"危险"则记跳过（不浪费门票） | `boss_personal:{today}` |
| 地图首领 map | 同上，每日 1 次，与个人首领共享碎片日上限 200，打完即记 | `boss_map:{today}` |
| 世界首领 world | 活动场次内 `boss/assist {bossKey}`，每场 assist N 次（默认 3，可配）；不在活动窗口则跳过；单场碎片上限 140 | `boss_world:{today}:{场次}` |

- 门票不足时跳过并记录，不动用捐献保留库存之外的购买手段。
- 奖励（含世界首领邮件结算）由下一轮收菜的 `mail/claim-all` 自然回收，无需专门处理。

**战前部署策略（preview/challenge 的配置项，本期落地为自动策略）**

逆向文档确认的可配置维度共 6 类：**出战技能、战术配置（输出优先/生存优先/均衡）、战前增益、挑战词缀、定向部位（仅本次）、材料加成**。逐类策略：

| 维度 | 小号策略 | 大号策略 |
|---|---|---|
| 战术配置 | 默认**均衡**；preview 显示生存评分明显低于输出 → 切生存优先 | 默认输出优先（装备靠养成自动化撑着） |
| 材料加成 | **养成资源 +35%**（farm 定位，碎片/材料最大化） | 视需求：farm 期同小号；冲装期选**定向装备品质提升一级** |
| 定向部位 | 不指定 | 当前穿戴评分最低的部位（客户端自动算短板） |
| 挑战词缀 | **不带**（稳过优先，门票珍贵） | preview 综合评分裕量 > 阈值时带 1-2 个（词缀=加难度换奖励，具体词缀 key 清单在 `bosses` section，联调确认 §5.13-12） |
| 战前增益/出战技能 | 默认配置 | 默认配置（手动调优入口保留） |
| 首领药剂 | `supply/equip bossPotion` 已在副职业循环（§5.6）就位，开场自动消耗 | 同左 |

> **关于"核心词缀"的调研结论**：逆向文档只确认"挑战词缀"作为 challenge 配置维度存在（加难度换奖励），**具体词缀 key 与数值没有写进文档**——它们在 `bosses` section 状态里下发（boss 视图加载 `bosses + professions` 两个 section）。能确定的相关规则：① preview 返回输出/生存/综合三项评分，是"带不带词缀、带几个"的决策依据；② 世界首领有**护盾**机制（药剂提供破盾+）；③ 失败返还挑战机会（门票不亏，但时间亏）。词缀 key 清单列入联调确认 §5.13-12，抓一次 `boss/preview` 真实响应即可补全，策略引擎预留词缀白名单配置位。

- 决策引擎统一走 `boss/preview`：小号"可胜才打"，大号"可胜且评分裕量够 → 加词缀再打"。

### 5.10 内部市场闭环（market_internal，小号↔大号，不做公开价格发现）

市场功能本期做，但**定位收敛为自家账号之间的内部传送带**——不碰公开市场的价格发现，所有交易对家都是自己的号：

```
大号侧（需求方）：
1. POST /api/market/create-buy-order  挂求购单（冻结预算）：缺的强化/洗练材料、装备胚子
   → 价格 = 内部价目表（参考价 × 系数，设置页可配，默认 1.0）
2. 求购积压超过 24h → update-price 按梯度提价（1.0 → 1.2 → 1.5，封顶可配）
3. 需求已满足/预算告急 → cancel 撤单解冻预算
4. 小号挂的装备/材料单 → buy {orderId} 收货（对家是自己小号，无价格波动风险）

小号侧（供给方）：
1. 每日检查大号的活跃求购单（my-orders / order-statuses 由大号侧状态缓存共享）
   → 背包里有匹配物品 → fulfill-buy-order {orderId, amount} 交付，金币回流小号
2. 溢出装备/材料按内部价 create-order 挂单，等大号 buy
3. 挂单 48h 未成交 → cancel 撤单，改走 §5.5 公会捐赠或 §5.4 分解（不恋战）
```

- **为什么内部闭环可行**：求购/交付的定价权在自己手里，不存在"乱挂反亏"；装备购入即用于大号养成（穿戴/继承销毁），不触发"购入转售锁定期 + 更高手续费"的惩罚（该惩罚只针对倒卖）。
- **风控边界**：内部价目表以参考价为锚（0.8-1.5 倍区间），不设离谱价格（异常价格转移 = 明显的工作室特征，风控红线）；每日内部成交笔数/金额设上限可配。
- 前置：`marketAccess` 门槛，未过的账号自动跳过并记录原因；货款到账走邮件，现有 `mail/claim-all` 回收。
- run_key：`market_list:{today}`（小号挂单）、`market_fulfill:{today}`（交付求购）、`market_buy:{today}`（大号收货）、`market_maintain:{today}`（改价/撤单巡检）。

### 5.11 大号养成自动化（reforge + enhance + inherit，仅大号）

大号的战力天花板靠洗练/强化/继承。客户端把这套人工流程自动化，**资源全部来自小号输血**（公会仓库 §5.5 + 内部市场 §5.10），形成完整内循环。每日流程（大号收菜后，按此顺序）：

```
1. 词条继承 affix-inherit（定向拿词，先于随机洗练）
   - 从背包/公会仓库挑"词条胚子"（小号捐的、含目标词条的装备）
   - affix-inherit-preview → affix-inherit {targetEquipmentId, sourceEquipmentId}（来源销毁，所以只用小号胚子，绝不用大号在役装备当来源）
2. 洗练补词 reforge（随机补剩余词条位）
   - reforge-preview → reforge {equipmentId, lockedStats[], targetStat}
   - 已命中的目标词条进 lockedStats，洗出新目标即更新锁定集
3. 强化 enhance（稳定提升基础属性）
   - enhance-preview → enhance {equipmentId, useProtectCharm}
   - 保护符策略：+11 起必用（阈值可配）；强化失败有保底计数（pity），连败时当日停手等保底价值最大化
4. 强化继承 enhance-inherit（换主装时迁移强化等级）
   - 默认关闭；开启后仅当 enhance-inherit-preview 显示收益明确时执行
   - 失败摧毁目标 → 元宝预算硬顶 + 每日最多 1 次 + 目标装必须是已锁定的毕业候选
5. 任一动作达到日上限或预算上限即停
```

**策略配置（设置页"大号养成"分组，只对大号生效）**：

| 配置项 | 键 | 默认值 | 说明 |
|---|---|---|---|
| 养成总开关 | `opt.growth_enabled` | 关 | 默认关，确认策略后手动开 |
| 部位清单 | `opt.growth_slots` | weapon | 只养成这些部位 |
| 目标词条优先级 | `opt.reforge_target_stats` | crit, critDamage, bossDamage | 继承/洗练共用的词条目标 |
| 洗练每日每件上限 | `opt.reforge_max_per_day` | 5 | 防上头 |
| 强化保护符起始等级 | `opt.enhance_protect_from` | +11 | 该等级起 enhance 必带保护符 |
| 强化每日每件上限 | `opt.enhance_max_per_day` | 3 | 连败即停，配合失败保底 |
| 强化继承开关 | `opt.enhance_inherit_enabled` | 关 | 高风险动作，单独开关 |
| 每日金币预算上限 | `opt.growth_gold_budget` | 50000 | 所有养成动作共享一个金币池 |
| 每日元宝预算上限 | `opt.growth_rare_budget` | 0 | 默认不动元宝（强化继承等元宝动作全停） |
| 毕业阈值 | `opt.growth_stop_quality` | 3 词条全目标 | 达到即该件毕业，跳过 |

- **安全边界**：只操作大号已穿戴/已绑定装备；所有动作 preview 必走不盲操作；来源销毁类（affix-inherit）的来源只许用小号胚子；毁装风险类（enhance-inherit）默认关闭且独立预算。
- run_key：`reforge:{today}:{equipmentId}` / `enhance:{today}:{equipmentId}` / `inherit:{today}` 计数；预算与次数判定以 runs 当日累计为准。

## 6. 调度引擎配套改造（120 号规模）

> 界面方案要支撑 120 个号，调度层必须配套，否则"立即同步一轮"要跑 10 分钟，体验断裂。

### 6.1 串行 → 受限并发

```rust
// one_pass 重构：账号任务用 JoinSet + Semaphore 限流
let sem = Arc::new(Semaphore::new(opts.concurrency)); // 默认 5
for acc in accounts {
    let permit = sem.clone().acquire_owned().await;
    set.spawn(async move { process_account(...).await }); // permit 随任务释放
}
```

- 并发数可配（设置页），默认 5：120 号一轮 ≈ 1.5-2 分钟，且对服务端压力可控
- **每账号请求间隔下限**（默认 800ms）：`Api` 层加 per-account 节流器，模拟真人操作节奏，风控友好
- `pass_busy` 防重入逻辑保留

### 6.2 失败退避

- runs 表记失败后，写 `meta.backoff:{account_id}:{task}` = 下次允许重试时间
- 退避序列：1min → 5min → 15min → 1h（封顶），成功后清除
- 会话失效重登、503 维护沿用现有逻辑，但计入退避，避免 120 号轮流撞墙

### 6.3 启动补跑

- 调度器启动时检查：大号的 `collect` 今日未完成且现在已过北京 06:00 → 立即排入首轮（现有逻辑已覆盖）
- 新增：练级中的小号若 `alt_level_last` 距今 > 30min（说明客户端关过机），首轮优先补一次练级

### 6.4 状态透出（给界面用）

- `Shared.latest` 扩展为结构化 JSON：`{tick, active: [{account_id, step}], pending: n}`
- 总览页可显示"正在处理 #37（练级中）"这类实时信息

## 7. 数据层改动（增量，不破坏现有 schema）

| 改动 | 说明 |
|---|---|
| `meta.opt.*` | 设置页所有配置，调度器每 tick 读取（启动时读入 + 设置保存时热更新） |

## 8. 技术实现要点

- **前端**：仍是纯静态三件套，不引入 Node/打包器（保持"全链路只有 cargo"的优势）。导航用 hash 路由（`#dashboard` / `#accounts` / `#guild` / `#logs` / `#settings`），约 +250 行 JS、+150 行 CSS
- **Toast 通知**替代所有 `alert()`：右上角浮层，成功绿色/失败红色，自动消失
- **后端新增 Tauri commands**：`get_settings` / `save_settings` / `get_pipeline_stats` / `get_accounts_detail`（带等级和下次动作）/ `retry_run`
- **SchedulerOpts 变为运行时读取**：`Shared` 内放 `RwLock<SchedulerOpts>`，设置保存时更新
- **玩法模块拆分**：`engine/` 下新增 `equip.rs`（换装+换图+分解模板）、`donate.rs`（材料+装备捐赠）、`profession.rs`（副职业循环+补给）、`reforge.rs`（大号洗装）、`boss.rs`、`arcade.rs`（含 lottery）、`market.rs`，与现有 `collect.rs`/`guild.rs` 平级；调度器按 §5.1 顺序编排，各模块只暴露 `run_if_due(db, api, acc, opts)` 一个入口，内部自己查 run_key 幂等
- **顺序硬约束**：调度器内 `decompose` 的调用点固定在 `equip` 与 `donate` 之后，代码评审时作为 checklist 项（防误销）

## 10. 明确不做（本期）

- 街机金币局的策略优化（加倍/分牌/追高奖励档）——默认只玩免费轮
- 公开市场的价格发现与倒卖（与第三方玩家的低买高卖）——市场只做自家账号内部闭环（§5.10），异常定价是风控红线
- 小号的洗练/强化/升品/继承——养成资源全部向大号倾斜，小号装备自动化止于换装/分解/捐赠
- 副职业加工类动作链与永久专精选择——默认只挂稳定采集；专精不可更改，留手动
- 公会共享仓库的自动 redeem——贵重决策，客户端只提醒（§5.5）
- Boss 战前增益与出战技能的手动调优——客户端按 §5.7 的自动策略表执行，深度调优留手动入口
- 任务/图鉴（quests/codex）自动领取——可领 key 列表待确认，下期并入 M5 同类工作
- 多大号/多公会支持——当前业务只有 1 个大号
- Keychain 存储 session_token——README 已标注，安全加固单列
- 打包分发优化（自动更新等）
